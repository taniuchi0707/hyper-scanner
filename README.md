# Hyper Scanner

スマホのカメラで書類を撮影し、傾きと影を補正して PDF にまとめるスキャナーです。
撮った画像はすべて端末の中で処理し、どこにも送信しません。

- **ブラウザ版**：https://taniuchi0707.github.io/hyper-scanner/
- **Android アプリ（APK）**：https://github.com/taniuchi0707/hyper-scanner/releases/latest/download/hyper-scanner.apk

## 使い始める

### Android アプリ
1. スマホで上の APK のリンクを開き、`hyper-scanner.apk` をダウンロードする
2. ダウンロードしたファイルを開く。「この提供元のアプリを許可」と出たら、Chrome（またはファイルアプリ）に許可する
3. 「インストール」を押す

Play プロテクトの確認が出たときは「インストールする」を選んでください（Google Play を通さずに配っているため出る表示です）。
新しい版を入れるときも、同じ手順で上書きインストールできます。撮ったページは消えません。

### ブラウザ版
上のアドレスを Chrome や Safari で開くだけで使えます。メニューの「ホーム画面に追加」で、アプリのように起動できます。

## できること

- **撮影**：カメラの映像から書類の四隅をその場で見つけて枠で示し、続けて何枚でも撮れる
  - **自動撮影**：枠が止まって手ぶれが収まると、自動でシャッターを切る（撮影画面の「自動」）
  - 書類のふちが画面からはみ出していると枠が橙色になり、「少し離して」と知らせる（このときは自動では撮らない）。書類が小さすぎるときは近づくよう促す
  - 枠は、似た候補の間で行き来してちらつかないよう、別の場所へ飛ぶときは続けて見つかってから動く
  - 対応端末ではライトも点けられる
- **範囲の調整**：四隅の丸をドラッグして合わせる。指で隠れる部分は拡大鏡で表示
- **傾きの補正**：斜めから撮った書類を、真上から見たまっすぐな形に直す。縦横比も斜めの具合から計算する
- **仕上げ**：くっきり（影と色かぶりを取る）／カラー／グレー／白黒（PDF では 1 ビット画像になり軽い）
- **ページの管理**：回転、順番の入れ替え、削除（元に戻せる）、撮り直し
- **PDF の書き出し**：用紙サイズ（自動 / A4 / B5 / レター）と画質（120 / 200 / 300 dpi 相当。撮った写真より細かくはならない）を選んで保存・共有
- Android アプリでは、ギャラリーなどの「共有」から写真を送って取り込める。PDF は「ダウンロード/Hyper Scanner」に保存される
- パソコンでは、画像のドラッグ＆ドロップや貼り付け（Ctrl+V）でもページを追加できる

### 設定（右上のメニュー）
- **書類の形**：自由 / A判・B判（1:1.41）/ レター（1:1.29）/ 名刺（1:1.62）
  形を選ぶと、その縦横比の四角形を見つけやすくなり、仕上がりもその比率にそろいます。
  比率がかけ離れた書類（レシートなど）は、選んだ形にかかわらずそのまま見つけます。
- **撮影方法**：
  - アプリ内カメラ … 四隅を見ながら続けて撮れる。見るための映像は軽い 1920×1440 にとどめ、撮るときは写真として撮る（長辺 4096 まで）。写真として撮れない端末では、撮る瞬間だけ映像を大きくして撮る。横倒しで返ってきた写真は画面の向きに直す。撮影画面の上に、映像と写真の大きさ（画素数）を表示する
  - カメラアプリ … 端末のカメラアプリで撮る。1枚ずつだが、いちばん高画質。撮ったあとに四隅を確かめる画面が開く
- **自動撮影**：オン／オフ

## 四隅の検出のしくみ

`js/detect.js`

1. 写真を縮小し、明るい部分を広げてから戻す「閉じ処理」で、紙の上の文字や罫線を消す。明るさの境目に加えて、色（彩度）の境目も使う（彩度は小さく閉じるだけにする。大きく閉じると木目のような模様の机の彩度が上がり、濃い書類との差が消える）
2. 四角形の候補を 3 通りで集める
   - 直線検出（ハフ変換）で見つけた直線を 4 本組み合わせる。同じ向きの直線の本数に上限を設け、布の格子柄やタイルの目地で候補が埋まらないようにする
   - 明るい紙の領域の凸包を四角形にまとめる
   - 模様の少ない塊（文字を消した紙の中は滑らか）を四角形にまとめ、内側と外側の広い帯の差がいちばん大きい位置に辺を合わせ直す（布の柄や木目の上の書類）。書類の中の写真で塊が切れたときのために、大きい塊どうしをまとめた四角形も出す
3. 候補ごとに点数をつける：四辺に沿って境目が続いているか、内側が外側より明るいか（細い線にだまされないよう、辺から離れた帯の平均で比べる）、内側が紙らしく均一か、ふちのすぐ内側が無地の余白か、角らしさ（境目が角のすぐ近くまであり、角の先で途切れるか）、面積、角の形、（指定があれば）縦横比。両隣の辺がどちらも先まで続いている辺（両端が T 字）は、書類の中の区切り（写真や表の上の線）とみなして点を下げる（書類が画面からはみ出したとき、途中までの四角形を書類と取り違えないように）
   - 直線ごとに「境目の強さ」と「両側の明るさ」の累積和を先に作っておくので、何千通りの組み合わせも引き算だけで採点できる
   - 上位の候補だけを、内側の様子まで含めて採点し直す
4. 上位の候補の各辺を、境目の位置に合わせて細かく直してから比べ直す
5. 書類の中の写真や表で切れた四角形より、辺を共有して外側を囲む四角形（書類全体）を選ぶ。何重にも区切られていれば外側へ順にたどる
6. 写真から探すときは、最後に長辺 1600 画素で、辺とほぼ同じ向きの境目だけを使って位置を合わせ直す。反った紙（辺が弓なり）のために、角の近くの点だけで引いた直線も見る
7. 撮影中は、直前に見つけた位置の近くを少しだけ選びやすくして、枠のぶれを抑える。画面の中ほどにある四角形も少し選びやすくする（周りに置いたほかの書類より、撮りたい書類を選ぶ）
8. 画面の中ほどがまわりより明らかに暗いとき（または、中ほどが暗く、明るい文字よりずっと暗いとき）は、地の色が濃い書類（紺の名刺など）かもしれないので、明るさを反転した画像でも探して点の高いほうを使う。反転しない画像では、濃い書類の中の明るい表や写真の枠がくっきりした四角形になって点が高く出やすいので、反転した画像でそれを囲む四角形が見つかれば、点が少し低くてもそちらを選ぶ。濃い書類は、仕上げを「カラー」から始める
9. 撮った写真から探すときは、撮影画面で枠を出していた位置も少し選びやすくする（画面で囲んでいた書類が仕上がりになるように）

縦横比は Zhang & He (2006) の方法で、カメラの焦点距離ごと見積もっています（`Geo.estimateAspect`）。

### 精度と速さの確かめ方
`npm start` のあと http://localhost:5173/tests/detect-bench.html を開くと、斜めから撮った書類の合成写真で、
本当の四隅とのずれを前の版と比べます。画面なしの Chrome でまとめて動かすこともできます。

```bash
node tests/run-bench.mjs "n=108&long=480&refine=1600" "n=108&real=1&long=384&quick=1" --rows
```

| 指定 | 内容 |
| --- | --- |
| `?n=108` | 場面の数（既定は 54） |
| `?long=480&refine=1600` | 写真から探すとき（撮影後）と同じ条件 |
| `?long=384&quick=1` | 撮影中の検出と同じ条件（遅い端末では 320） |
| `?real=1` | 実際の撮影でよくある邪魔を足す（書類を押さえる指、照り返し、反った紙、暗い部屋、手ぶれ・ピンぼけ） |
| `?out=1` | 書類の一部を画面の外に出す（ふちに触れる四角形を返して「はみ出し」を知らせられるかを数える） |
| `?clutter=1` | 周りにほかの書類を 1〜3 枚、画面のふちにかけて置く |
| `?edge=1` | 紙の厚みでできる、ふちのすぐ外の薄い影を足す |
| `?darkdoc=1` | 地の色が濃い書類（紺の名刺のように、地が暗く文字が明るい）にする |
| `?fill=0.7-0.92` | 書類が画面に占める割合を変える |
| `?only=%2301,%2302` | 場面を絞り込む（`--dump` で点数の内訳、`--shot=フォルダ` で画像） |
| `?timing=1` | 処理の段階ごとの時間 |
| `?track=1` | 撮影中の「追いかけ」が、近くの位置を正しく合わせ、ずれた位置を受け入れないかを数える |

108 場面で、四隅のずれが長辺の 0.8% 未満になった割合と、5% を超えて大きく外れた場面の数です。

| | ふつう | 実際の邪魔あり（`real`） | 周りにほかの書類（`clutter`） | 地の色が濃い書類（`darkdoc`） |
| --- | --- | --- | --- | --- |
| 写真から探すとき（v1.0.4） | 78.5%（大外れ 17） | 72.0%（21） | 59.8%（38） | 0.9%（95） |
| 写真から探すとき（今の版） | **93.5%**（1） | **91.6%**（3） | **86.0%**（9） | **80.4%**（9） |
| 撮影中（v1.0.4） | 76.6%（18） | 66.4%（21） | 59.8%（38） | 3.7%（90） |
| 撮影中（今の版） | **91.6%**（1） | **83.2%**（3） | **85.0%**（9） | **86.0%**（5） |

書類の一部が画面の外に出ている 99 場面（`out`）では、撮影中は 90 場面で画面のふちに触れる枠を返して「はみ出し」を知らせます。書類の中の四角形を書類と取り違えるのは 3 場面です（以前は 8 場面）。
撮影中の v1.0.4 は長辺 320 画素、今の版は 384 画素です（遅い端末では 320 に下がり、88.8%・78.5%・79.4%）。
撮影中の「実際の邪魔あり」で外れる多くは、反った紙で四隅が 1% ほどずれるもので、撮ったあとの写真では最後の合わせ直しで直ります。
1 回の時間はパソコンで、写真から探すとき約 70ms、撮影中の検出で約 40ms（追いかけているときは約 16ms）です。
CPU を 4 分の 1 の速さにした目安（`--throttle=4`）では、写真から探すとき約 310ms、撮影中の検出で約 170ms（追いかけ約 90ms）です。どれもワーカーで動くので、画面は止まりません。

まだ見つけにくいのは、次のようなときです。
- 白い紙の上に白い書類が重なっていて、上の紙のふちがほとんど見えない（重なった紙、机の上のほかの書類の上）
- チェック柄の布の上の、写真入りの書類
- 地の色が濃い書類を、暗い机の上に置いたとき

## 動作の軽さ

撮影画面が重くなるいちばんの原因は、大きすぎる映像でした。4096×3072 の映像は、端末がコマを運ぶだけで重く、
1 コマを縮めて取り出すたびに画面側が止まります。今は次のようにしています。

- 見るための映像は 1920×1440 にとどめ、画質は写真として撮って確保する（写真が撮れない端末は、撮る瞬間だけ映像を大きくする）
- 開いてから映像が実際に届くコマ数を数え、1 秒に 15 コマを下回る（端末が運びきれない）ときは、見るための映像を 1280×960 に下げる
- 撮影中の検出には、映像のコマを複製せずにそのままワーカーへ渡し（`VideoFrame`）、縮めるのもワーカーの中で行う
- 検出は 1 秒に約 12 回まで。枠が止まっている間は半分に減らし、撮影中（写真の処理中）は止める。1 回の検出に時間がかかる端末では、検出の解像度を 384 から 320 に下げる
- 書類を見つけ続けている間は、4 回に 3 回は直前の位置を合わせ直して確かめるだけにする（画面全体を探す約半分の時間）。点が下がったときと、別の場所の候補が出たときは画面全体を探す
- 枠は変わったときだけ描き直す。撮影中は裏のページ一覧を描かない。アニメーションは transform だけで動かす
- 撮った写真の取り込みは、元画像の JPEG 書き出しと四隅の検出を並べて進め、検出とサムネイルは 1600 画素に一度だけ縮めたものから作る
- 仕上げ（くっきり・グレー・白黒）と補正は、行ごとの計算の使い回しと、四隅を囲む範囲だけの読み出しで軽くした（PDF の 1 ページで約 0.7 秒 → 約 0.5 秒）
- PDF の書き出しは、コアとメモリに余裕のある端末ではワーカー 2 つで 2 ページずつ進める（25 ページで 8.7 秒 → 4.0 秒）
- 写真として撮るときは、対応端末でフラッシュを使わない（書類の照り返しを防ぎ、撮影も早く終わる）

重い処理（撮影中の検出、撮った写真の縮小・向きの補正・四隅の検出、仕上げの見本、PDF 用の画像）は、
すべて Web Worker（別のスレッド）で行い、画面の描画と操作を止めません（`js/jobs.js`）。
ワーカーの中身は各部品の関数をそのまま組み立てて作るので、別ファイルを読めない Artifact 版でも同じように動きます。
ワーカーが使えない古い環境では、同じ処理を画面側で行います。

| 4000×3000 の写真を取り込む間 | 画面が止まった最長時間 | かかった時間 |
| --- | --- | --- |
| 画面側で処理（v1.0.3） | 421ms | 2.6 秒 |
| ワーカーで処理（v1.0.4） | 8ms | 0.6 秒 |
| ワーカーで処理（今の版） | 2ms | 0.33〜0.49 秒 |

枠は画面の書き換えのたびに、検出した位置へなめらかに近づけて描きます。
撮影画面の重さは `tests/camera-load.js`（別スレッドで作った NV12 の映像を本物のカメラの代わりに流す）で測れます。

`node tests/e2e.mjs` は、画面なしの Chrome でアプリを一通り動かして確かめます（代わりのカメラで撮影画面を開き、枠と案内・追いかけ・なめらかさ・自動撮影・手動の撮影・一覧・PDF の書き出し）。
`--throttle=4` で画面側の CPU を 4 分の 1 の速さにできます。パソコンでは前の版も今の版も 1 秒に約 56 コマで動き、
スマホで重かった原因（4096×3072 の映像をカメラから運ぶ負担）は再現できないので、実機での確かめが必要です。

## 動かし方（開発）

Node.js があれば、追加のパッケージなしで動きます。

```bash
npm start
```

`http://localhost:5173/` を開きます。同じ Wi-Fi のスマホからは、表示される `http://192.168.x.x:5173/` を開いてください。
http で開いたときはブラウザの中でカメラが使えないため、シャッターを押すと端末のカメラアプリが開きます。

| コマンド | 内容 |
| --- | --- |
| `npm start` | 動作確認用のサーバー |
| `npm run icons` | `icons/` と Android のアイコンを作り直す |
| `npm run build:artifact` | claude.ai の Artifact 用の 1 ファイル版を `dist/` に作る |
| `npm run sync:android` | Web 版のファイルを Android アプリにコピーする |

## Android アプリのビルド

`android/` は、Web 版をそのまま WebView で動かす入れ物です（`MainActivity.java`）。
画面はアプリ内の https のアドレスで開くので、カメラや保存はブラウザ版と同じ仕組みで動き、
PDF の保存・共有、写真の受け取り、戻るボタンだけをアプリ側で受け持ちます。

`main` に push すると GitHub Actions（`.github/workflows/android.yml`）が APK をビルドし、リリースに載せます。
署名鍵はリポジトリの Secrets（`HS_KEYSTORE_B64` / `HS_KEYSTORE_PASSWORD` / `HS_KEY_ALIAS`）に入っています。
手元の `android/keystore/` にある元の鍵はリポジトリに含めていません。なくすと、アプリを上書き更新できなくなります。
